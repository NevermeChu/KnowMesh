# 开发问题记录

本文只记录值得长期保留的重要开发问题：跨层架构、权限与安全边界、数据一致性、生命周期不变量、兼容性，以及具有实际风险的运维问题。

不记录局部 UI 调整、普通功能补齐、一次性调试结论、依赖安装过程、可从单个短函数直接读出的缺陷，或特定提交、CI 运行和临时验收状态。

## 1. Workspace 类型与项目分类形成重复权威来源

### 问题
项目曾同时保存 Workspace 归属和 Personal/Collaboration 分类，权限模式存在两个事实来源，也无法稳定表达多个 Team Workspace。

### 根因
早期项目分类同时承担界面分区、资源归属和权限聚合职责；引入真实 Workspace 后，旧分类没有随职责上移而移除。

### 解决方法
以 `workspaces.kind = personal | team` 作为权限模式的唯一持久化来源。Project 只保存 Workspace 归属，Personal/Collaboration 仅作为服务端推导出的界面概念。

## 2. 成员角色存在但资源权限没有统一执行

### 问题
Workspace、Project 和 Document 入口各自比较角色，曾导致相同角色在不同入口获得不一致能力。

### 根因
角色同时用于所有权展示和操作授权，缺少统一能力模型与服务端授权入口。

### 解决方法
集中定义角色到资源能力的映射，所有服务端入口重新计算授权；客户端能力只控制界面呈现，不作为安全边界。

## 3. Personal Workspace 生命周期与永久性不变量不一致

### 问题
Personal Workspace 曾依赖首次进入工作台才创建，初始化与身份创建不能共享事务，删除接口还允许物理删除个人空间。

### 根因
身份生命周期、补偿初始化、Workspace 类型和删除能力分别实现，没有共同围绕“每个用户有且仅有一个永久 Personal Workspace”设计。

### 解决方法
用户创建和 Session 建立调用同一幂等初始化服务，以数据库唯一约束阻止重复创建；服务端拒绝删除或退出 Personal Workspace，客户端也只依据 `workspace.delete` 能力显示删除入口。

## 4. 身份提供方邀请与 Workspace 邀请存在双重状态

### 问题
身份提供方管理应用级邀请，本地数据库管理 Workspace 授权，两套状态在撤销、过期和接受时可能不一致。

### 根因
邮件投递、应用注册和 Workspace 成员授权被绑定到同一个外部邀请对象，但三者拥有不同生命周期和资源边界。

### 解决方法
身份系统只负责注册、登录和验证邮箱；Workspace 邀请与授权由本地数据库管理，邮件服务只负责投递本地一次性令牌。

## 5. 移除 Workspace 成员可能破坏 Project 所有权不变量

### 问题
成员移除与 Project 创建并发时，可能出现 Project owner 已不属于上级 Workspace 的孤立资源。

### 根因
所有权和成员身份分散存储，检查曾位于事务外，竞争操作没有锁定同一成员关系。

### 解决方法
成员移除与 Project 创建在事务内锁定相同 Workspace 成员行并重新授权；用复合外键保证 `(workspace_id, owner_id)` 指向有效成员关系。

## 6. Project 权限无法区分直接授权与 Workspace 来源

### 问题
Project 权限界面曾对 Workspace 来源成员提供 Project 角色修改和移除操作，产生无效操作或意外直接授权。

### 根因
权限结果缺少稳定来源字段，客户端只能看到最终角色。

### 解决方法
服务端明确返回 `project | workspace` 来源；Project 成员操作只适用于直接授权，Workspace 来源回到 Workspace 权限边界管理。

## 7. Workspace 结构发现与 Project 正文权限混用

### 问题
Team Workspace 成员曾自动获得全部 Project 和 Document 正文能力，使 `project_members` 无法成为内容访问门槛。

### 根因
同一读取能力同时表达导航结构发现和正文读取，Workspace 角色与 Project 直接角色又被无条件合并。

### 解决方法
结构发现使用独立能力；Project 和 Document 正文能力只由直接 Project 成员关系授予，服务端在读取正文前重新授权。

## 8. Project 成员关系无法证明属于同一 Workspace

### 问题
仅包含 `project_id` 和 `user_id` 的成员表无法阻止跨 Workspace 建立 Project 成员关系。

### 根因
成员表缺少可参与复合外键的 `workspace_id`。

### 解决方法
保存并校验 `workspace_id`，通过 Project 与 Workspace 成员两个复合外键建立数据库约束；迁移先回填并预检既有数据。

## 9. Owner 权威字段与 owner 成员角色可能失配

### 问题
资源表的 `owner_id` 与成员表的 `role = owner` 可能指向不同用户，也可能出现 owner 被降级、删除或存在多个 owner。

### 根因
该约束是跨表、双向并允许事务内暂时失配的不变量，普通外键和 `CHECK` 无法完整表达。

### 解决方法
使用 owner 部分唯一索引限制数量，并以延迟约束触发器在提交时验证最终一致状态；创建和转让在同一事务完成。

## 10. 账户删除与资源退出缺少统一生命周期规则

### 问题
账户删除、Workspace 退出、Project 退出和 owner 资源清理由不同入口执行，容易遗留关系或破坏所有权不变量。

### 根因
身份系统与业务资源没有共享生命周期服务，删除逻辑按入口逐步添加，容易遗漏新增关联表。

### 解决方法
使用统一幂等的资源移除服务：Personal owner 随账户删除完整个人资源，普通成员只退出；仍拥有 Team Workspace 的用户必须先转让所有权，账户删除复用同一规则并清理全部用户关联。

## 11. 登录流程可能丢失邀请接受地址

### 问题
未登录用户从邀请链接进入认证流程后，可能被固定重定向到 Dashboard，丢失原始路径和令牌。

### 根因
受保护路由没有保留当前站内目标，身份系统默认跳转又可能覆盖普通参数。

### 解决方法
保留完整站内目标并拒绝绝对 URL、协议相对 URL 和反斜杠路径；将校验后的地址作为认证回跳目标，回跳时不得自动接受邀请。

## 12. 邀请、通知与站内操作没有形成闭环

### 问题
用户可能收到邀请或审批通知，却无法站内处理或直达对应权限界面；仅依赖邮件 Token 还会使已登录用户无法接受。

### 根因
通知只保存展示快照，邀请接口只支持外部令牌，查询结果缺少操作所需资源上下文。

### 解决方法
同时保留外部令牌和已认证用户两条处理路径；通知返回必要资源标识，支持站内操作和深度链接，并在业务事务中同步通知状态。

## 13. 浏览器最近文档缓存未按用户和权限隔离

### 问题
同一浏览器切换账户或权限被撤销后，本地缓存仍可能展示旧文档元数据或正文片段。

### 根因
缓存键不含用户身份并持久化完整结果，读取时没有通过服务端重新授权。

### 解决方法
客户端只按用户隔离保存文档 ID；面板打开时由服务端重新验证读取权限并过滤失效资源。缓存不能作为授权来源。

## 14. 账户身份删除与业务清理不在同一事务

### 问题
认证系统先执行业务清理、再独立删除身份时，后一步失败会留下仍可登录但业务资源已经消失的账户。

### 根因
认证生命周期回调不共享业务清理事务。

### 解决方法
由应用入口重新认证，并在同一数据库事务中清理业务数据和身份记录；任一步失败整体回滚。

## 15. 资源删除会遗留通知死链和待处理关系

### 问题
Workspace 或 Project 删除后，历史通知可能仍指向不存在的资源；移除成员也可能遗留邀请和访问申请。

### 根因
通知使用无物理外键的多态目标，级联删除无法自动处理，成员移除事务也没有覆盖相关表。

### 解决方法
资源删除事务保留历史快照但清空通知目标，并清理关联邀请和申请；新增资源类型必须加入删除生命周期测试。

## 16. 邀请同步缺少幂等性

### 问题
邮箱验证、页面预取或重复邀请可能为同一用户和 Workspace 生成重复邀请及通知。

### 根因
同步流程按记录逐条插入，没有按收件人和资源去重。

### 解决方法
邀请创建和通知同步都以收件人及资源为幂等边界，拒绝重复有效邀请，并在通知写入前检查既有状态。

## 17. 实时通知缺少事务语义和跨实例传递

### 问题
进程内广播可能在事务回滚后仍通知客户端，也无法覆盖连接与业务写入位于不同实例的部署。

### 根因
内存事件不具备提交语义、跨进程传输和持久状态校准能力。

### 解决方法
数据库在提交后发布最小失效信号，各进程重新读取持久状态再向本地连接扇出；首次连接和重连始终从数据库校准。

## 18. 所有权变化期间的成员操作可能使用过期授权

### 问题
所有权转让与成员修改并发时，等待中的操作可能在 owner 已变化后继续执行。

### 根因
授权在事务外完成，相关操作没有共同锁定资源主记录。

### 解决方法
写操作先锁定 Workspace 或 Project，在锁内重新校验 owner 和能力；数据库延迟约束作为最终防线。

## 19. 审计写入与业务变更可能不一致

### 问题
业务修改和审计分开提交会产生成功变更但缺少历史的状态；客户端二次筛选还可能错误显示某类记录不存在。

### 根因
审计没有加入业务事务，筛选和分页也没有成为服务端查询边界。

### 解决方法
关键变更与审计在同一事务提交，筛选和分页由服务端执行；文档只描述真实的数据保留保证。

## 20. PGlite Socket 不能证明真实 PostgreSQL 跨连接通知

### 问题
本地 PGlite 可以验证持久数据，但不能可靠模拟多个 PostgreSQL backend 之间的异步通知。

### 根因
Socket 适配层复用单一 PGlite 引擎，与真实 PostgreSQL 独立连接模型不同。

### 解决方法
PGlite 只验证其真实支持的事务行为；跨连接通知、双会话实时交互和权限撤销必须在真实 PostgreSQL 上验收。

## 21. 外部邮件失败可能留下无效邀请通知

### 问题
如果站内通知先于邮件发送提交，邮件失败后的补偿撤销无法收回已投递 Toast。

### 根因
外部邮件不参与数据库事务，提前广播把未完成的副作用当成已完成事实。

### 解决方法
首个事务只创建邀请；邮件成功后重新确认邀请有效，再写入去重通知。邮件失败只撤销并审计。

## 22. ProseMirror JSON 与 Y.Doc 往返会进行 Schema 规范化

### 问题
合法 JSON 转为 Y.Doc 再投影时可能补齐默认属性，严格对象相等会把语义等价内容误判为损坏。

### 根因
Transformer 通过完整 Schema 解析和序列化节点，默认属性会被规范化。

### 解决方法
转换前后使用完整 Schema 并验证内容；测试比较规范化后的稳定快照，不依赖属性省略形式。

## 23. 独立协作进程不能继承 Next.js 运行假设

### 问题
独立服务曾复用 `server-only`、完整 Auth 实例和 Next.js 环境加载方式，并假设 HTTP hook 能接管内置响应；生产制品也未完整包含协作服务。

### 根因
框架模块、认证副作用、环境来源、HTTP 生命周期和发布制品没有与独立 Node.js 边界分离。

### 解决方法
只复用无框架依赖的数据库、Schema 和最小 Session 验证配置；`.env` 仅在存在时加载，健康端点独立提供，应用与协作服务由同一 release 部署和回滚。

## 24. Team 文档正文可能形成多个权威写入路径

### 问题
Team 文档初始化 Yjs 时，普通 JSON 保存仍可能并发写入；功能关闭或服务不可用时也可能错误回退到单人写入。

### 根因
编辑模式、功能开关、协作状态和正文权威类型被混为一体，客户端状态参与决定服务端写入边界。

### 解决方法
服务端只按 Workspace 类型决定正文引擎：Personal 使用 JSON，Team 始终拒绝普通正文写入。协作不可用时 Team 只读显示最近成功投影，不启用备用写入。

## 25. Yjs 状态可能被静默标记为新 Schema 版本

### 问题
加载旧状态时若不检查版本，后续保存可能在没有迁移的情况下把它标记为当前版本。

### 根因
版本字段只参与初始化，没有成为加载和更新条件。

### 解决方法
加载和持久化都要求版本一致；不兼容状态拒绝打开，升级只能通过显式 Yjs 迁移完成。

## 26. 协作服务关闭可能在存储失败后无限等待

### 问题
存储失败会让文档留在内存，而服务销毁等待文档卸载，可能无法结束或丢失退出前更新。

### 根因
关闭流程无法等待明确持久化结果，也缺少截止时间和逐资源错误收集。

### 解决方法
停止接收连接后逐文档等待最终持久化，再按截止时间销毁；前一步失败不得跳过后续释放，最终以非零状态暴露失败。

## 27. 长连接权限与 Session 快照会过期

### 问题
成员角色、Session 或 Document 状态变化后，既有连接不会自动获知；正常 Session 续期又不能被误判为撤销。

### 根因
连接保存握手快照，数据库变更信号本身也不能证明连接已经失效。

### 解决方法
数据库只发布失效线索，协作进程重新查询当前身份和权限；正文写入前强制复查并以周期复查兜底，仅在有效级别变化时关闭。

## 28. 服务端撤销写权限后客户端仍可能本地假写入

### 问题
服务端关闭旧写连接后，客户端若继续使用页面初始权限，编辑器仍可能接受不会同步的本地内容。

### 根因
客户端没有把协作 scope、Provider 关闭和断线纳入运行时编辑能力。

### 解决方法
客户端初始只读，页面授权与服务端 `read-write` scope 同时成立才可编辑；认证失败、关闭或撤销立即冻结正文和相关工具栏。

## 29. Yjs 字段约定不一致会破坏正文投影

### 问题
客户端与服务端读取不同 XmlFragment 时，实时同步看似成功，但二进制状态和 JSON 投影会分离。

### 根因
客户端依赖默认字段，服务端固定读取 canonical 字段，旧状态中的惰性类型又可能跳过兼容迁移。

### 解决方法
两端显式使用同一 canonical 字段；加载旧状态时先具体化旧字段，再迁移为只包含 canonical 正文的新 Y.Doc。

## 30. 单篇文档持久化失败可能被其他文档掩盖

### 问题
保存失败的文档可能被卸载，其他文档成功又可能错误恢复 readiness；关闭循环也可能在首个错误后跳过后续文档。

### 根因
健康度使用全局计数，没有与具体文档生命周期关联，也缺少逐文档错误边界。

### 解决方法
按文档记录失败并自动重试，恢复前阻止卸载；readiness 依据失败文档集合，关闭时逐篇尝试并收集全部错误。

## 31. Windows 进程清理可能丢失更新或遗留服务

### 问题
直接终止进程树会绕过协作持久化；异步清理又可能随外层终端退出，遗留 Next.js、PGlite 或自定义端口进程。

### 根因
npm 包装层和控制台信号不能可靠传递应用级关闭语义；启动流程也曾把已有监听误判为新子进程 readiness，预检失败后仍进入无子进程的端口清理，从而可能回收另一套运行栈。

### 解决方法
在启动任何子进程前检查本次需要的全部端口，占用时直接失败且不进入清理；通过 IPC 请求优雅关闭，并用独立清理进程管理其余子进程，只有本次实例实际启动过受管进程时才允许清理，等待持久化截止时间后才强制终止。

## 32. 协作编辑器生命周期可能产生无主连接和重复 Presence

### 问题
启动或离开再进入 Team 文档时，浏览器可能报告 `WebSocket is closed before the connection is established`，并遗留仍占用协作端口但已不再服务当前文档的无主连接。重复进入文档后，连接可能继续累积，Awareness 也可能使同一用户重复显示。正文产生本地 Yjs 更新后，界面会先进入“保存中”；如果当前房间没有通过稳定连接收到服务端持久化回执，该状态就无法收敛为“已同步”或“保存失败”。

### 根因
客户端同时存在两个不同职责的 Provider：`HocuspocusProviderWebsocket` 是传输层，负责一条真实 WebSocket、重连和房间消息复用；`HocuspocusRoom` 创建的 `HocuspocusProvider` 是文档房间层，负责指定 Y.Doc 的认证、同步、Awareness 和未同步更新计数，并在挂载时把房间附加到传输层。旧实现让传输层在 React 渲染期构造，并保留库默认的立即连接行为。React Strict Mode 会重复执行开发模式的初始化流程，其中被丢弃的传输实例没有对应的 Effect 清理机会；同时，传输构造器发起的异步连接尚未把状态推进到连接中时，房间层附加又可能看到未连接状态并再次要求连接。两个连接流程会互相替换或提前关闭，其中一条便触发建立前关闭警告，另一条还可能脱离当前房间生命周期。房间 Provider 与外层传输同时卸载时，如果传输先销毁，房间也无法完成关闭消息和 Awareness 分离。保存状态又依赖房间收到协作服务发回的持久化无状态消息，因此连接竞争会直接表现为长期“保存中”，而不只是控制台噪声。

### 解决方法
不在渲染期构造传输。外层 Effect 先经过短暂稳定窗口，再以 `autoConnect: false` 创建唯一的 `HocuspocusProviderWebsocket` 并交给房间层；等待房间完成附加后，由生命周期控制器显式调用一次 `connect()`，使传输构造和房间附加不再分别触发连接。Strict Mode 清理会取消尚未执行的构造或连接定时器，因此被丢弃的挂载不会产生真实 Socket。卸载时先让文档 Provider 发送关闭消息、移除 Awareness 并从传输层分离，再异步销毁外层传输。回归测试必须覆盖 Strict Mode 丢弃流程、稳定挂载只连接一次和卸载后销毁；Presence 继续按稳定用户 ID 防御性去重。

## 33. 认证表单在客户端接管前可能把凭据写入 URL

### 问题
表单在 hydration 前提交时，浏览器可能执行默认 GET，把邮箱和密码放入地址栏、历史和访问日志。

### 根因
表单只依赖客户端事件，没有安全 HTML 提交方式作为无 JavaScript 兜底。

### 解决方法
所有凭据表单显式使用 POST；客户端接管前也不得把具名凭据序列化到 URL，并以无 JavaScript 测试固定该边界。

## 34. 共享数据库中的 E2E 固定资源会产生并发污染

### 问题
多个浏览器项目或 worker 复用相同身份和资源 ID 时，会互相删除状态、触发权限失效或唯一键冲突。

### 根因
夹具使用模块级固定常量，没有把 worker 和单个测试视为独立数据库租户。

### 解决方法
每个测试建立完整且唯一的身份与资源并独立清理；只有确需跨浏览器证明的行为才跨引擎运行。

## 35. 单个连接复查异常会跳过后续权限撤销

### 问题
批量复查时，前一条 Session 或权限查询失败可能中断循环，延迟其他用户的权限撤销。

### 根因
错误边界包围连接集合而不是单条连接。

### 解决方法
逐连接独立捕获脱敏错误；只有明确失效的连接才关闭，单条失败不得阻止后续处理。

## 36. 搜索路径无法同时保证正确性和可扩展性

### 问题
对 ProseMirror JSONB 模糊匹配会命中结构字段；未转义通配符改变语义，B-Tree 无法支持前置通配符，固定上限还会使结果不可达。

### 根因
检索缺少纯文本投影、合适索引和统一分页契约。

### 解决方法
保存时维护纯文本投影，转义 LIKE 特殊字符，使用 Trigram GIN 索引；服务端返回总数和分页元数据。

## 37. 生产环境首次引导无法由仓库完整重建

### 问题
自动 release 依赖服务器预先存在的 systemd、Nginx、证书、数据库、部署用户和 sudoers，空服务器无法仅凭仓库恢复。

### 根因
CI/CD 只交付增量 release，首次配置没有被作为可重复验证的基础设施交付物。

### 解决方法
区分 release 与人工 bootstrap，逐步版本化完整配置、受限 sudoers 和幂等检查脚本；不得覆盖未经审查的现场改动。

## 38. 生产 PostgreSQL 缺少可验证的备份与恢复链路

### 问题
缺少异地副本、保留策略、告警和恢复演练时，主机故障可能同时丢失数据库和本机备份。

### 根因
部署流程只负责迁移和应用回滚，把数据库持久性当成未验证的外部条件。

### 解决方法
定义异地备份、加密、保留周期、RPO 和 RTO，监控任务及备份新鲜度，并定期执行真实恢复演练。

## 39. 生产部署账户与网络边界没有落实最小权限

### 问题
无范围 sudo、直接 root SSH、边界不明的防火墙和缺少沙箱的服务会把发布链路扩大为整机控制面。

### 根因
发布依赖远程内联 root 操作，尚未收敛为可最小授权的稳定入口，网络与进程基线也未统一版本化。

### 解决方法
发布逻辑收敛为 root-owned helper，sudoers 只允许必要操作；只开放预期公网端口，内部服务监听 loopback，并保留救援与回滚路径。

## 40. Windows 本地服务的后代进程可能创建可见终端

### 问题
`npm run dev` 启动期间可能反复出现终端窗口；关闭其中一个窗口会终止对应服务，并触发整个本地运行栈退出。

### 根因
编排器虽然隐藏了直接子进程，但只把预加载器地址写入环境变量而没有让 Next.js CLI 实际加载它；内部 `fork` 或 `spawn` 派生的服务进程因此没有继承 Windows 隐藏窗口选项。

### 解决方法
协作服务由 Node 直接加载 TypeScript；Next.js 保留官方 CLI，并在 CLI 参数中显式导入 Windows 预加载器，让内部 `fork` 与 `spawn` 派生进程强制隐藏。所有长生命周期服务仍由编排器记录、监控并统一销毁；真实 Windows 验收必须覆盖启动、热重载和整栈退出。

## 41. 全站响应缺失安全响应头

### 问题
`next.config.ts` 未配置任何 `headers()`，Nginx 片段也只覆盖 WebSocket 代理；所有页面都没有 HSTS、`X-Frame-Options`、`X-Content-Type-Options`、`Referrer-Policy` 和 `Permissions-Policy`，点击劫持、MIME 嗅探、SSL 降级和 Referer 泄露均无浏览器侧防护。

### 根因
安全响应头从未被纳入应用或反代配置，构建配置只关注功能与代理转发。

### 解决方法
在 `next.config.ts` 中为全站路由统一注入上述五个安全响应头；页面请求再由 `src/proxy.ts` 生成请求级 nonce 和严格脚本 CSP，Next.js 自动为根布局主题脚本与框架脚本应用同一 nonce，避免应用组件重复传递浏览器会隐藏的属性。Google Fonts 改由锁定的 Fontsource 包同源发布，不向 CSP 加入外部样式或字体来源。动态渲染取舍记录在 ADR 0013。

## 42. 文档正文缺少大小与嵌套深度限制

### 问题
正文校验与纯文本提取均为无界递归，超深嵌套或超大内容可造成栈溢出与持续 CPU 消耗，形成认证用户可触发的拒绝服务面。

### 根因
结构校验只关注合法性，未限制序列化体积和递归深度；Server Action 请求体上限也未显式声明。

### 解决方法
校验前先做序列化体积上限检查，递归校验器携带并检查最大深度，同时在构建配置中显式固定请求体上限。

## 43. 业务表用户引用列没有外键约束

### 问题
通知、偏好、收藏、成员、邀请、访问请求及 Workspace/Project 的 owner 列均为裸字符串，绕过应用路径的删除会留下孤儿行，完整性完全依赖手工清理清单。

### 根因
Better Auth 字符串 ID 引入时只做了应用层补偿清理，未同步补齐数据库引用约束。

### 解决方法
按归属语义为各列补充对 `user.id` 的级联或置空外键，审计触发者与哨兵化的创建者列作为已记录例外保持无外键；迁移先清理孤儿行再建约束。

## 44. 本地运行时以强制终止结束 PGlite

### 问题
关闭本地环境时数据库进程仅有两秒优雅窗口即被整树强杀，未完成检查点的写入曾两次损坏本地数据目录。

### 根因
统一的两秒关停超时未区分嵌入式数据库的检查点耗时。

### 解决方法
将数据库进程的优雅退出窗口延长至十五秒，仅在确认子进程仍未退出后才强制终止。

## 45. 项目邀请没有过期时间

### 问题
项目邀请插入时不设置过期时间且接受时不校验时效，长期滞留的旧邀请仍可被接受。

### 根因
邀请过期机制只在 Workspace 邀请上实现，Project 邀请复制流程时遗漏了该维度。

### 解决方法
插入时写入七天过期时间，接受与可见性判断均校验未过期，迁移为存量邀请按创建时间回填。

## 46. 协作服务对每条写同步消息重复查询权限

### 问题
每条写同步消息都执行会话与权限查询，百人协作文档会产生数百 QPS 的自伤式数据库负载。

### 根因
撤销延迟目标被错误下推到了每条消息粒度，而实际只需有界延迟。

### 解决方法
连接上下文记录最近复核时间，写消息复核按三秒间隔节流，最坏撤销延迟由该间隔加周期扫描共同兜底。

## 47. 时间戳列使用无时区类型

### 问题
任何非 UTC 会话时区的直接 SQL 都会使存量值发生偏移，历史数据的语义依赖运行环境配置。

### 根因
Schema 默认生成 `timestamp without time zone`，正确性依赖应用始终传 UTC 的隐式约定。

### 解决方法
全部时间戳列改为 `timestamptz`，迁移显式在 UTC 时区下转换存量值。

## 48. 已删除协作内容的剥离依赖库默认值

### 问题
评审曾推断持久化快照永久保留已删除文本；字节级探针证明当前快照并不含墓碑载荷，但该隐私属性完全隐式依赖 Hocuspocus 默认 `yDocOptions.gc = true` 与 Yjs GC 行为，配置或升级变化可能让留存无声回归。

### 根因
关键不变量从未被显式声明，评审结论也未先经实测验证。

### 解决方法
在协作服务构造中显式声明 `yDocOptions: { gc: true, gcFilter: () => true }`，并在文档中标注改动前须重新评估；不引入运行时压缩机制，避免维护一个当前恒为空操作的路径。

## 49. 越权访问个人项目会触发应用错误

### 问题
其他用户直接访问 Personal 项目或文档地址时，数据读取会被拒绝，但页面显示 Next.js Application Error 而不是资源不存在。

### 根因
页面并行执行资源可见性查询和访问状态查询；前者尚未把不可见资源转换为 404，后者已经抛出未处理的 `AuthorizationError`。

### 解决方法
页面先完成资源可见性查询并对不可见资源调用 `notFound()`，只有可见项目才继续查询访问状态；使用另一名已认证用户覆盖 Personal 项目和文档的 Not Found UI、`noindex` 与无应用错误回归测试。Next.js 流式响应在响应头已发送后会保留 HTTP 200，不能把状态码单独作为该路径的拒绝证据。

## 50. 同类资源流程独立复制导致事务语义逐渐分叉

### 问题

工作区邀请的链接接受与站内接受路径分别维护成员写入、邀请状态、通知、审计和通知已读逻辑，且九处成员操作各自手写关联通知更新；三个命名资源创建弹窗和 Landing 区块标题也重复维护同一交互或展示骨架。

### 根因

实现按入口和资源类型横向增长，只复用了底层 UI 与数据库函数，没有在稳定的领域步骤和展示结构形成小型共享边界；同时 Project 与 Workspace 的权限差异使整体泛型化风险较高，导致局部重复长期未被治理。

### 解决方法

邀请接受统一进入同一个加锁事务，关联通知更新和邀请期限使用共享领域 helper；命名资源弹窗与 Landing 居中标题复用共享组件。保留 Project 与 Workspace 各自的授权、成员不变量和所有权事务，不建立掩盖领域差异的通用成员管理引擎。

## 51. PostgreSQL 长期连接干净断开后不会恢复

### 问题

通知和协作权限失效的 `LISTEN` 连接以及协作单实例租约只监听 `error`；数据库或连接代理干净关闭连接时进程继续把已经完成的启动 Promise 当作有效，实时链路或单实例护栏可能静默失效。

### 根因

长期连接生命周期错误地把异常事件当作唯一断线信号，没有同时处理 node-postgres 在连接结束时发出的 `end`。

### 解决方法

三个长期连接同时监听 `error` 和 `end`；任一事件都清除连接与启动状态。两个 `LISTEN` 订阅器进入同一有上限退避重连路径，租约连接结束则触发协作服务失败关闭；主动释放前移除监听器，避免正常关闭被误判为故障。

## 52. Personal 文档整篇保存会静默覆盖并发修改

### 问题

多个标签页基于不同快照编辑同一 Personal 文档时，后保存者会无条件覆盖整篇 ProseMirror JSON，永久丢失先提交标签页的修改。

### 根因

Personal 正文保持低成本整篇 JSON 持久化，但保存协议没有版本令牌或乐观锁条件，事务行锁只能串行化写入，不能识别保存者使用了过期基线。

### 解决方法

正文保存必须携带页面读取或上次成功保存返回的 `updated_at`；事务锁行后比较版本，不一致时返回冲突并保留本地未保存内容，成功时返回新版本供后续保存使用。Personal 标题编辑器也携带版本以避免与正文保存互相制造过期基线；Team 标题不能复用会随协作正文变化的该令牌。

## 53. Workspace 删除会销毁最关键的审计历史

### 问题

Workspace 删除没有对应审计动作，且 `audit_logs.workspace_id` 使用级联外键；删除资源会同时抹除它的全部历史，使最破坏性的操作无法追溯。

### 根因

审计日志被建模为活跃 Workspace 的普通子资源，而不是需要跨业务资源生命周期保留的不可变事件；删除流程也没有在事务中记录最终动作。

### 解决方法

审计日志继续保存非空 Workspace UUID，但移除对活跃 Workspace 的外键依赖；显式删除在同一事务写入 `workspace_deleted` 后删除资源，任一步失败均整体回滚。数据库集成测试必须证明旧历史与删除事件在 Workspace 消失后仍然存在。

## 54. Team 文档标题脱离协作状态并静默互覆

### 问题

Team 正文通过 Yjs 实时合并，标题却只在当前标签页调用 Server Action 并刷新自身；其他协作者的输入框、面包屑和导航保持旧值，并发保存会以后写覆盖先写。

### 根因

标题不属于 Y.Doc 是 ADR 的有意边界，但独立持久化路径没有自己的版本令牌和提交后广播；复用文档 `updated_at` 又会被频繁的协作正文投影更新制造误冲突。

### 解决方法

标题继续由 Server Action 持久化，新增独立递增的 `title_version` 做乐观并发控制。数据库提交后发布标题事件，协作进程按文档房间广播 stateless 消息；无本地修改的客户端更新输入框并刷新服务端导航，有本地修改的客户端保留输入并显示冲突。标题纳入页面隐藏、组件卸载和浏览器离页保护，不进入 Y.Doc。

## 55. 分数排序间隙耗尽与并发创建会破坏同级顺序

### 问题

文档拖拽反复取相邻 `sort_order` 中点时，浮点间隙最终无法继续细分；并发创建同一父节点下的文档也可能读取相同末尾值并写入相同顺序。

### 根因

排序值由客户端快照或事务外查询推导，服务端没有在共同锁边界内检查相邻间隙、重新编号同级节点或串行化尾部追加。

### 解决方法

所有创建与移动在事务中锁定项目行并重新验证权限。移动同时锁定目标同级节点；当相邻间隙小于安全阈值或数值接近安全精度边界时，按固定步长重新编号并写入服务端计算的顺序。创建在同一项目锁内读取末尾值，使并发请求依次追加。

## 56. 协作周期快照留下不可捕获硬崩溃窗口

### 问题

协作进程在两次完整快照之间被 `SIGKILL`、OOM 或主机故障终止，且浏览器随后关闭时，最近一次成功持久化后的正文更新可能永久丢失。

### 根因

未落库更新只存在于协作进程和浏览器内存；优雅关闭与进程内重试都无法覆盖不可捕获终止，服务端又没有逐更新持久日志。

### 解决方法

协作进程以 PostgreSQL advisory lock 强制数据库级单写实例，持久化失败时保持 readiness 失败、阻止文档卸载，并要求运维避免强制重启或切换发布。通过服务端 `read-write` 认证后，让 `y-indexeddb` 按用户、文档和 Schema 版本持久化 Provider 的同一个 Y.Doc；重新打开后把本地更新经当前服务端授权重新合并。断网继续只读，退出或删除账户尽力清理该用户缓存。本地副本丢失时仍只能恢复服务端快照，因此它缩小而不消除 RPO；需要无客户端保证时必须另行设计服务端持久更新日志。

## 57. 共享布局全量文档导航随工作区线性膨胀

### 问题

访问任一工作区页面都会读取全部项目的所有文档元数据并发送完整递归树；大型工作区的首屏查询、序列化和客户端树构建随文档总数线性增长。

### 根因

共享 Layout 同时承担项目发现和文档树加载，导航没有分页、节点加载状态或深层直达路径；客户端拖拽还依赖已加载的兄弟快照计算排序中点。

### 解决方法

共享 Layout 只读取项目。文档节点按 `projectId + parentId` 使用 `(sort_order, id)` 游标分页并独立重试，直接访问深层文档只读取带循环和深度限制的祖先路径；创建、删除和移动后局部刷新受影响节点。拖拽只提交位置语义，由服务端在锁内基于完整同级集合计算顺序，数据库索引补齐 `id` 稳定排序列。

## 58. 搜索页码查询缺少唯一排序并读取完整正文投影

### 问题

搜索只按相关度和更新时间进行 offset 分页，同分同时间记录没有唯一顺序，可能跨页重复或遗漏；查询还为每个结果读取完整 `search_text`，只在应用层截取短摘要。

### 根因

首版搜索优先复用了页码 UI 和应用层摘要函数，没有把稳定分页的最终键和数据库到应用的数据传输量纳入查询契约。

### 解决方法

增加文档 ID 最终排序键并限制 offset 边界，使用参数化 SQL 只返回摘要窗口；只有真实规模测量证明需要时再采用稳定游标或 PostgreSQL 全文搜索。

## 59. 工作区数据失效缺少按数据域划分的所有权

### 问题

文档、项目、成员、Workspace 和偏好等写入普遍失效整个工作区布局，部分客户端同时修改局部状态并调用路由刷新，导致无关数据重复读取且刷新职责不清晰。

### 根因

统一布局失效最初提供了低成本正确性保障，但导航已经改为按节点加载后，写入路径仍没有区分 Workspace 上下文、Project 列表、文档节点、权限概览和偏好等数据所有者。

### 解决方法

建立写入到数据域的失效清单，为每个操作确定唯一刷新所有者，先删除能够证明重复的刷新；只有相关查询实际使用 Next cache 时才引入按域 tag，不以细粒度为目的增加无效缓存层。

## 60. Better Auth Session 核心配置存在双重维护

### 问题

主应用和独立协作进程分别创建 Better Auth 实例并重复数据库 adapter、base URL 和 secret 等核心配置，未来 Session 或 cookie 配置变化可能只更新一端。

### 根因

协作进程需要避免加载邮件和用户初始化副作用，因此没有复用完整主认证实例；实现同时缺少一个不带副作用的共享 Session 配置边界。

### 解决方法

提取纯 Better Auth 核心配置构造器供两个实例组合，主应用继续追加邮件、rate limit 和生命周期 hook，协作进程保持最小依赖并继续绕过 cookie cache 重新验证 Session。

## 61. CI 和部署脚本缺少确定且可复用的执行边界

### 问题

CI 缓存整个 `node_modules` 并在命中时跳过 `npm ci`，覆盖率没有质量门槛；生产制品、远程激活与回滚逻辑集中在大型 workflow，CI 与 Release 还分别维护相似的制品打包步骤。

### 根因

工作流同时承担依赖安装优化、质量门禁、制品构建和部署程序职责，缺少从 lockfile 重建依赖、共享制品入口和可独立测试的版本化部署脚本。

### 解决方法

只缓存 npm 下载并始终执行 `npm ci`，基于当前关键模块覆盖率建立可解释门槛；统一 CI/Release 制品脚本，再把远程激活与回滚提取为严格校验的版本化脚本，workflow 仅保留编排、环境和 Secret 边界。

## 62. 生产迁移可能在确认回滚目标前执行

### 问题

自动激活在现有 `current` 软链接缺失、损坏或指向 release 根目录外时，仍可能先执行不可自动回滚的数据库迁移，随后才因没有可用旧版本而停止。

### 根因

激活脚本把旧 release 的解析与边界校验放在迁移程序之后，测试只覆盖了迁移自身失败时不切换应用，没有覆盖迁移前置条件缺失。

### 解决方法

在运行迁移程序前解析并验证旧 release 存在且位于 release 根目录内；缺少有效回滚目标时立即停止，并用 node 桩断言迁移没有执行且没有写入回滚标记。

## 63. 制品清理只排除顶层环境文件

### 问题

standalone 子目录中的 `.env*` 文件可能绕过顶层清理和检查并进入生产 tgz，破坏制品不得携带环境配置或 Secret 的约束。

### 根因

打包脚本删除顶层 glob，并以 `find -maxdepth 1` 检查残留；冒烟 fixture 也只创建顶层 `.env.local`。

### 解决方法

递归删除整个 standalone 树中的 `.env*` 文件，并在归档前递归拒绝任何残留同名路径；冒烟测试同时放置顶层与嵌套环境文件并验证二者都不进入制品。

## 64. 文档递归查询在应用层才判定规模上限

### 问题

祖先路径和移动子树即使最终被应用拒绝，数据库仍会先完整遍历超深或超大层级并把全部结果返回，异常数据可能造成不受业务上限约束的计算、内存与传输成本。

### 根因

递归 CTE 只用访问路径阻止循环，100 层和 10,000 个后代的限制在查询完成后才由 TypeScript 检查。

### 解决方法

祖先递归只生成上限加一行以判定超深；后代查询只消费根节点、允许的后代和一条超限哨兵。应用继续在任何写入前拒绝超限结果，保留循环、项目边界和事务原子性检查。

## 65. 文档移动在事务内沿用陈旧的来源项目授权

### 问题

文档移动在事务外解析来源项目，事务内只重新验证该项目权限却不确认文档仍属于它；并发移动可能让后到事务基于旧来源权限覆盖较新的位置，反向跨项目移动还可能以相反顺序获取项目锁。

### 根因

事务把授权时读取的资源归属当成稳定身份，项目权限锁、文档行锁和最终更新条件没有形成同一个一致性边界，多个项目也缺少统一锁序。

### 解决方法

按项目 ID 稳定排序锁定来源和目标项目并在事务内重新验证权限，再锁定且确认文档仍属于授权时的来源项目；来源变化时返回冲突，最终更新继续携带来源项目条件。

## 66. 收藏切换的读取后写入无法收敛并发请求

### 问题

服务端先读取收藏是否存在再决定插入或删除；两个并发切换可能读取相同旧状态，随后发生唯一键冲突或返回与数据库最终状态不一致的结果。

### 根因

接口只表达“切换”意图，没有携带调用方期望的目标状态，并把一次逻辑操作拆成了不受共同原子语义保护的读取和写入。

### 解决方法

让客户端提交明确的收藏目标状态；收藏使用联合主键 `ON CONFLICT DO NOTHING`，取消收藏按联合键删除，使重复和同目标状态并发请求幂等。

## 67. Excalidraw 浏览器边界和字体资产默认值与应用运行约束冲突

### 问题

Excalidraw 包在模块初始化时访问 `window`，且未配置资产路径时从外部 CDN 加载字体；Next.js 开发态服务端评估会直接失败，外部字体则被现有 CSP 拒绝。

### 根因

仅使用 Client Component 不会自动禁止 Next.js 对动态组件的服务端评估，Excalidraw 的默认字体基址也不符合 KnowMesh 只允许同源字体的 CSP。

### 解决方法

白板编辑器使用 `ssr: false` 动态加载，并在导入 Excalidraw 前设置同源资产路径；依赖安装后从锁定包复制字体到被 Git 忽略的公共资产目录，部署继续保持原 CSP。

## 68. 同一数据库上的两个协作写进程不能共用一条咨询锁

### 问题
Team 富文本和 Team 白板都需要“每个数据库只有一个写实例”，如果复用同一对 `pg_try_advisory_lock` 键，后启动的服务会拿不到租约并失败关闭。

### 根因
单写租约最初只为 Hocuspocus 进程设计，锁命名空间和锁 ID 写死在文档协作模块内，没有把“租约机制”和“某个写服务的身份”分开。

### 解决方法
抽出共用的 `acquireCollaborationLease`，按服务传入不同的 `lockNamespace`/`lockId` 和丢失回调；文档协作与白板协作继续各自持有独立连接上的 session advisory lock。

## 69. CSP 只放行协作 URL 的 HTTP origin 会拦住 Socket.IO WebSocket

### 问题
Team 白板客户端使用 `http://`/`https://` 作为 Socket.IO 入口，浏览器实际发起 `ws://`/`wss://` 连接；`connect-src` 若只写入 `URL.origin`，页面会显示同步失败，而协作服务的鉴权失败计数仍为 0。

### 根因
CSP `connect-src` 按 scheme 匹配。Hocuspocus 的公开地址本身是 `ws://`，因此旧策略碰巧够用；Socket.IO 的公开地址是 `http://`，升级传输后 scheme 变化，浏览器在握手到达服务端之前就拦截连接。

### 解决方法
对每个协作 URL 同时加入对应的 HTTP(S) 与 WS(S) 源；生产 WSS 终端同样成对放行。

## 70. Playwright `webServer.env` 覆盖后丢失真实 PostgreSQL 验收环境

### 问题
只声明 `PORT` 和 `NEXT_PUBLIC_APP_URL` 时，子进程拿不到调用方设置的 `E2E_REAL_POSTGRES` 等变量，本地运行器会再拉起 PGlite 并与已占用的 5432 冲突，LISTEN/NOTIFY 与权限失效也无法按真实 PostgreSQL 验收。

### 根因
Playwright 在配置了 `webServer.env` 后不再默认传入完整 `process.env`；白板验收还要求协作服务监听 Windows 上 `localhost` 可能解析到的 IPv6 环回，仅绑定 `127.0.0.1` 时 Socket 对不上。

### 解决方法
`webServer.env` 先展开 `process.env` 再覆盖端口与应用 URL；E2E 将协作服务绑到 `::`。真实 PostgreSQL 验收必须显式设置 `E2E_REAL_POSTGRES=true`，禁止本地运行器再启动 PGlite。

## 71. 冻结的白板保存队列会阻止进程重启后恢复写入

### 问题
协作服务关闭时客户端会冻结保存队列。Socket.IO 重连后仍把同一队列拿去接收 baseline；队列在冻结后忽略后续 canonical，界面可能显示已同步，实际无法再入队保存。

### 根因
冻结被设计成权限撤回后的永久停写，没有区分“服务暂时不可用后的新会话”。baseline 处理把重连当成同一队列的 revision 更新。

### 解决方法
每次收到 baseline 都丢弃旧队列，按当前 canonical scene 与 revision 新建保存队列；冻结队列的忽略语义保持不变，由新队列承接重启后的写入。

## 72. 已注册邮箱再次注册会伪装成功且不发验证邮件

### 问题

已存在账户再次提交注册时，页面仍可完成提交流程，但不会发出验证邮件，原先还会显示“账号已创建”等成功文案，使用者无法区分新注册与邮箱已被占用。

### 根因

Better Auth 在 `requireEmailVerification` 开启时对重复邮箱返回合成成功响应（`token: null` 的伪造用户），不抛 `USER_ALREADY_EXISTS_USE_ANOTHER_EMAIL`，也不调用验证邮件发送，以避免注册接口被用于探测邮箱是否存在。前端把无错误码的注册响应一律当成新账号已创建。

### 解决方法

保留该防枚举行为，不向客户端暴露邮箱是否已注册。注册提交成功后只显示中性提示：若该邮箱可注册，将收到验证邮件；打开邮件链接后自动登录。已注册邮箱继续不发信，文案也不再声称账号已创建。

## 73. 指令面板 E2E 用 Ctrl+K 打开会与 hydration 和页面拦截竞态

### 问题
协作栈上的指令面板韧性用例在 CI 中等不到「快捷指令面板」对话框，整次检查失败，依赖其成功的生产 Deploy 被 skip。

### 根因
`CommandPalette` 只在客户端 `useEffect` 里注册 Ctrl/Cmd+K。用例在 `goto` 后立即按键，并在打开前对 `**/personal**` 安装 Playwright route。Linux runner 上按键可能落在监听注册之前；过宽的 `/personal` 拦截还会碰到打开面板时发往当前页的 Server Action，对话框从未挂载。

### 解决方法
先点击侧栏「主要导航」里的「搜索」（走 `openCommandPalette`），再断言对话框。模拟过期搜索的 route 必须在面板打开之后安装，且只延迟带共享检索词的 POST。

## 74. Toast 状态变化会重建团队白板连接并覆盖未保存笔迹

### 问题

团队白板打开期间，任意普通或站内通知 Toast 的出现与自动消失都会让 Socket.IO 连接重新建立。服务端随后发送的 baseline 可能覆盖尚未成功进入保存队列的本地笔迹，造成用户可见的数据丢失。

### 根因

`ToastProvider` 每次列表变化都会创建新的 context 对象，`TeamWhiteboardEditor` 的连接 effect 又依赖整个 toast 对象。引用变化触发 cleanup，旧保存队列被销毁、socket 断开；新连接收到 baseline 后按 canonical scene 重建队列和画布，而已被销毁队列中的本地状态无法参与冲突调和。

### 解决方法

让 Toast context 分发器及无 Provider 时的 no-op 对象保持稳定，跟踪并在手动关闭或卸载时清理自动移除定时器。白板连接 effect 通过 Effect Event 调用最新 Toast 分发器，不把 toast 对象作为连接生命周期依赖；保留 baseline 以 canonical scene 初始化新会话的既有语义。浏览器回归必须覆盖 Toast 出现和自动消失期间只存在一条白板 websocket。

## 75. CI 构建与生产部署共享权限边界并允许配置回退

### 问题

普通 build 和独立 Release artifact job 都挂载 production environment；手动 CI 可以从任意分支进入生产 Deploy。部署主机、用户、路径、服务名和可信指纹还存在仓库字面量或缺省回退，配置缺失时可能继续连接旧目标，而不是在改变生产状态前失败。

### 根因

workflow 把“验证代码”“生成制品”和“获得生产部署权限”作为同一环境边界维护，并把特定服务器配置当成仓库默认值。分支判断只区分 push，没有对 `workflow_dispatch` 应用同样的生产来源约束，也没有统一的配置完整性预检。

### 解决方法

只有 deploy job 挂载 production environment；build 与 Release 从 repository Secret/Variable 获取构建所需公开配置。push 只监听 `main`，手动 CI 只有选择 `main` 才能部署。所有部署目标、路径、服务名、功能开关和可信指纹都由 GitHub production environment 显式提供，并在构建、SSH、迁移之前统一验证；真实主机和指纹不得写入仓库。

## 76. 默认构建命令隐式执行数据库迁移

### 问题

调用者只想验证生产构建时，`npm run build` 会先执行 `db:migrate`，可能修改当前 `DATABASE_URL` 指向的数据库。构建失败与迁移失败也被绑定为同一操作，难以判断构建是否本身可通过。

### 根因

package script 把迁移当成生产构建的固定前置步骤，没有区分纯编译、带临时数据库的本地集成构建与受回滚前置条件保护的生产激活迁移。

### 解决方法

默认 `build` 只调用 `build:next`。需要验证迁移与构建组合时使用 `build-local`，由本地运行器启动临时 PGlite 后迁移并构建；生产迁移继续只由 release 激活脚本在确认有效回滚目标后执行。

## 77. 侧边栏拖动宽度会高频重渲染整个应用外壳

### 问题

桌面端拖动侧边栏调整宽度时，每个 `pointermove` 都更新 `AppShell` 的 React state，使工具栏、文档编辑器、命令面板等整个认证应用外壳随指针频率重复渲染。复杂文档与协作页面上会放大拖动卡顿和无关组件工作的风险。

### 根因

侧边栏把实时视觉预览和需要 React 持有的最终宽度当成同一状态：拖动回调直接调用 `setSidebarWidth`，而 CSS 变量又由该 state 生成。高频、仅影响布局的临时值因此进入了组件树的渲染路径。

### 解决方法

拖动期间只在应用外壳 DOM 节点上更新受上下限约束的 `--app-sidebar-width`；`pointerup` 才把最终值提交到 React state。`pointercancel` 恢复已提交值，键盘调整和双击复位继续直接提交，并用浏览器回归覆盖拖动预览、释放提交、键盘步进与双击复位。

## 78. 公开页面被迫加载工作区中日韩与等宽字体资源

### 问题

未登录用户访问落地页或认证页时也会获得 Noto Sans SC 与 JetBrains Mono 的字体样式入口。生产构建中这组工作区字体包含 107 个文件、约 4.6 MB 的可请求资源，公开页面不使用代码编辑与工作区中文排版，却仍进入对应资源图。

### 根因

根 layout 同时导入 Plus Jakarta Sans、Noto Sans SC 和 JetBrains Mono，Next.js 因而把三套字体都视为所有路由的共同依赖。落地页内联字体栈还声明 Noto Sans SC，使公开页面的实际字体意图与加载边界无法分离。

### 解决方法

根 layout 只保留公开页面使用的 Plus Jakarta Sans，把 Noto Sans SC 与 JetBrains Mono 的导入下沉到认证工作区 layout，并让落地页字体栈只声明实际加载的拉丁字体及系统回退。通过生产构建的路由客户端清单和未登录 `/` 响应验证：公开页面只引用公共 CSS，工作区字体 CSS 仅出现在工作区路由。

## 79. 文档编辑器分发层把协作客户端装入单人文档 chunk

### 问题

打开 Personal 富文本文档时，浏览器会加载包含 Hocuspocus、Yjs 协作连接与恢复逻辑的编辑器分发 chunk，即使该文档只使用 JSON 保存。拆分前该 chunk 约 219 KB，单人编辑路径承担了无关的协作解析与下载成本。

### 根因

`DocumentEditorDispatcher` 虽然已经动态加载白板，但静态导入了单人 Tiptap 与协作 Tiptap 两个实现。外层 `DocumentWorkspace` 的一次动态导入只能切开“未选择文档”和“选择文档”，无法继续按运行时编辑模式形成独立 chunk。

### 解决方法

在分发层分别动态导入单人 Tiptap、协作 Tiptap 与白板，并为两种富文本编辑器复用既有骨架屏。生产构建确认分发层约 9.9 KB，Personal 编辑器约 12.5 KB 且不含 Hocuspocus 或 Excalidraw，协作实现单独成约 174 KB chunk；浏览器回归覆盖 Personal 保存与离开时刷新、Team 富文本协作以及 Team 白板同步。

## 80. 视觉偏好写入会失效根布局或整个工作区布局

### 问题

用户切换主题或内容宽度时，服务端在写入数据库和 cookie 后还会失效根 layout 或工作区 layout。一次纯视觉偏好操作因此触发与项目导航、通知和活动文档无关的服务端布局重算，并扩大活动编辑器与协作连接接收刷新负载的范围。

### 根因

偏好 Server Action 沿用了“写入后统一 `revalidatePath`”的模式，没有区分已由客户端即时应用并由 cookie 在下次请求前恢复的视觉状态，与必须从服务器重新查询的项目或权限集合。根布局和工作区布局失效对当前交互没有提供额外正确性。

### 解决方法

主题和内容宽度写入只持久化数据库与 httpOnly cookie，不再失效根布局或工作区布局。客户端继续乐观更新 `data-theme`、暗色 class 与 `--content-read-width`，失败时回滚；浏览器回归验证两项偏好写入期间活动编辑器 DOM 不被替换，cookie 正确保存且刷新后恢复。

## 81. 文档树写入用工作区布局失效代替节点刷新

### 问题

标题、创建、删除和移动文档都会调用 `revalidatePath('/(workspace)', 'layout')`，使只改变一个导航父节点的操作重新计算项目列表并向整个工作区发送布局刷新。该行为扩大活动编辑器和协作连接的刷新面，也与按节点加载导航树的既有架构约束不一致。

### 根因

文档树从全量首载迁移为按父节点分页后，四个写入动作保留了旧的统一 layout 失效。客户端已经掌握创建目标、移动来源与目标，标题和删除也能确定原父节点，但这些信息没有汇入统一的局部导航刷新边界。

### 解决方法

移除四个文档写入的工作区 layout 失效。创建成功后先导航到新文档，由选中路径加载并合并对应父节点；移动继续重载来源和目标父节点；标题保存、远端标题广播与删除通过受类型保护的客户端事件只重载原父节点。项目与 Workspace 列表变化仍保留 layout 失效，不把客户端树状态当作结构或权限权威。

## 82. PGlite 集成测试手写迁移清单会静默漏掉新迁移

### 问题

每次新增 Drizzle 迁移时还必须人工把 SQL 文件名追加到 PGlite 测试帮助器。若遗漏，所有依赖该帮助器的集成测试仍可能通过，但运行的是落后于生产的数据库结构，无法覆盖最新约束和索引。

### 根因

测试运行器复制维护了第二份迁移顺序，而 Drizzle 已在 `migrations/meta/_journal.json` 中保存权威、有序的迁移标签。两份清单之间没有自动一致性检查。

### 解决方法

PGlite 测试帮助器直接按 Drizzle journal 的 entries 顺序生成 SQL 文件名，移除手写数组。新增迁移只维护 Drizzle 生成物；任一 journal 条目缺少对应 SQL 时，集成测试在读取阶段立即失败。

## 83. 移除 Workspace 成员的项目清理查询数随项目数量线性增长

### 问题

移除 Workspace 成员时，会对 Workspace 下的每个项目依次删除该用户的权限申请、邀请和项目成员关系。一个包含 N 个项目的 Workspace 因而产生 3N 次 DELETE；项目较多时会延长事务持锁时间，并扩大成员治理操作对数据库连接的占用。

### 根因

实现先查询 Workspace 的项目 ID，随后用逐项目循环表达三类关联数据清理，没有利用三张表都以 `project_id` 和 `user_id` 作为删除条件的集合特征。

### 解决方法

保留 Workspace 所有权与成员记录的事务锁、项目所有者约束、通知和审计顺序，只把项目范围清理改为三条 `project_id IN (...) AND user_id = ...` 删除；空项目集合跳过这三条语句。增加真实迁移 PGlite 集成测试，覆盖成员在同一 Workspace 的多个项目中同时存在申请、邀请和成员关系的清理结果。

## 84. 团队白板持续编辑会绕过防抖并触发致命限流断线

### 问题

用户在 Team 白板中持续拖动或绘制时，Excalidraw 会为同一次交互连续触发 `onChange`。实测绘制 2 个元素可产生约 48 次完整场景保存，保存数量与用户交互持续时间和回调频率相关，而不是与最终元素数量相关。

当任一连接在 10 秒内超过服务端 20 次保存上限时，服务端会断开该 Socket.IO 连接。canonical 广播及恢复型 `onChange` 还可能使另一个浏览器继续回写相同场景，最终两个协作端都显示「已离线，等待重连」，服务指标下降为 `activeConnections = 0`。由于这是服务端主动断开，Socket.IO 客户端不会自动重连，用户只能刷新页面恢复协作。

### 根因

这是一个事故链，而不是单一限流参数不合理。第一，编辑器把拖动、缩放、多点绘制和文字编辑期间的每次 `onChange` 都交给保存队列。原有 250 毫秒静默防抖只约束首次保存；一旦保存已经开始，期间到达的新场景会被标记为 pending，而保存循环在收到确认后立即发送最新场景，后续变化实际绕过了静默窗口。

第二，服务端提交成功后会把 canonical scene 广播给房间内客户端。客户端调用 Excalidraw `updateScene` 后只用一个 microtask 清除“正在应用远端场景”标记，但 Excalidraw 的恢复型 `onChange` 可能晚于该 microtask，并且 restore 还会补充默认元素字段。该回调因此可能被误判为新的本地编辑，在两个客户端之间形成 canonical → `updateScene` → `onChange` → save 的回声循环。

第三，服务端达到频率上限时直接执行强制断开，没有向客户端返回可识别的背压结果和重试时间。Socket.IO 将服务端主动断开视为终止连接，不会进入普通网络中断的自动重连流程，所以一次合法编辑突发会被放大为永久离线。

### 解决方法

保存队列使用共享的 750 毫秒尾随静默窗口。首次变化、保存进行期间的新变化以及远端 canonical 合并后仍待提交的变化都经过同一窗口；一次保存成功后不再立即循环发送 pending scene。版本冲突仍使用 canonical revision 和官方 `reconcileElements` 在有界重试循环内协调，不改变 Team 白板的 revision/CAS 权威。

客户端应用远端场景时记录元素 `id`、`version`、`versionNonce`、`isDeleted` 与可持久化 appState 组成的版本指纹。restore 补充默认样式或内部字段不会改变该指纹；只要后续 `onChange` 仍与远端基线一致，无论回调出现一次还是多次，都被识别为恢复回声并忽略。真实元素编辑会提升版本，可持久化画布设置也会改变指纹，此时才清除远端基线并进入保存队列。保存队列判断本地、canonical 与保存中场景是否相同时也复用该语义指纹，不再用完整 JSON 差异把 restore 字段误判为新编辑。两层判断共同避免依赖 microtask 时序、固定回调次数或 Excalidraw 不稳定的瞬态字段。

协议和服务端在保存窗口已满时返回包含 `retryAfterMs` 的非致命 `rate-limited` 确认，并保持 Socket.IO 连接。客户端保留最新待保存场景，在退避时间结束后自动重试；服务端通过 `rateLimitedSaves` 指标暴露背压事件，便于区分客户端合并异常、滥用流量和数据库持久化失败。

测试覆盖保存请求进行期间的场景合并、限流确认与自动退避、canonical 回声后的空闲稳定，以及两个隔离浏览器会话持续慢速绘制时的保存次数、在线成员、连接数和同步状态。既有只读权限、项目角色降级、Workspace 成员移除、会话撤销和 toast 生命周期回归同时保留。

## 85. 团队白板把远端画面传播阻塞在自动保存与数据库提交之后

### 问题

一个用户在 Team 白板中绘制、移动、缩放或删除元素时，另一个用户不会在操作过程中看到变化。只有本地用户停止产生 `onChange`、自动保存静默窗口结束、完整 scene 成功写入 PostgreSQL 并返回保存确认后，对端才收到 canonical scene。该延迟即使在同机浏览器和低延迟网络中也稳定存在；持续拖动还会不断重置 750 毫秒尾随窗口，使对端长时间停留在旧画面。这使已经标记为“实时协作”的白板表现为延迟批量刷新，并把数据库负载和瞬时网络问题直接转化为协作画面停顿。

### 根因

客户端只有一条 scene 出站路径：`TeamWhiteboardEditor` 将每次有效 `onChange` 交给 `TeamWhiteboardSaveQueue`，队列在尾随防抖后通过带 ACK 的 `save` 事件发送完整 scene。服务端完成消息校验、写权限复查和 `document_whiteboard_states` revision CAS 事务后，才向房间其他连接广播 canonical。实时传播、冲突协调和持久化确认因此被错误地串成同一条同步流水线。

这一设计把“数据库确认后的持久化权威”误当成“其他协作者第一次看到变化的必要条件”。直接缩短或取消保存防抖不能解决架构问题：Excalidraw 在一次拖动中会产生大量变化，若每次都提交完整 scene，会重新引入保存风暴、CAS 冲突、限流和数据库持锁压力。直接高频广播完整 scene 也不可接受，因为白板允许 10,000 个元素和数 MiB 载荷，拖动单个元素不应重复传输整个画布。

### 解决方法

把临时实时状态与持久化权威拆成两条协议路径。本地变化仍进入 750 毫秒完整 scene 保存队列，由 PostgreSQL revision CAS、保存 ACK 和提交后 canonical 维护持久化权威；同时进入独立实时发布器。发布器按元素 `id`、`version`、`versionNonce` 与 `isDeleted` 跟踪已知版本，在 33 毫秒窗口内只发送最后一帧中真正变化的元素、删除 tombstone 和可持久化 appState，拖动结束时立即冲刷。实时消息带连接内单调序号，服务端完成 Schema、频率和当前写权限检查后直接转发，不访问数据库，也不把临时状态冒充为新的 canonical revision。

接收端按服务端连接 ID 与序号拒绝旧包，使用 Excalidraw 公共 `restoreElements` 和 `reconcileElements` 将增量合并进当前画布，并用 `CaptureUpdateAction.NEVER` 应用，避免远端编辑污染本地 Undo/Redo。保存成功后的 canonical 继续负责确认、并发冲突纠偏和重连恢复；实时包丢失时，后续元素版本、canonical 或 baseline 会恢复一致性。服务端分别记录已转发和因频率上限丢弃的实时 scene 数量，使体验延迟、异常客户端频率与数据库保存问题可以独立诊断。测试必须证明实时 scene 在 revision 未增长时已经转发，同时保留 CAS、冲突、viewer 只读、权限撤回和重启基线测试。

## 86. 团队白板光标使用可靠全量 Presence 广播放大网络抖动和渲染开销

### 问题

用户移动鼠标或拖动元素时，对端虽然能看到光标，但经常表现为停顿、跳跃和追赶。延迟网络会加重现象，但即使连接稳定，客户端高频回调、服务端全量扇出和 React 重渲染也会消耗主线程与序列化预算。房间成员增加后，每个用户的每次光标变化都会向整个房间发送包含所有成员的新数组，单个高频增量被放大为与房间规模相关的重复载荷。

### 根因

`onPointerUpdate` 原先没有任何节流，直接使用普通 Socket.IO `emit` 发送坐标。普通事件会在传输暂不可用时进入缓冲；恢复后已经过时的中间坐标仍可能依次到达，于是对端播放历史位置而不是尽快显示最新位置。服务端还把光标保存在成员对象内，每收到一个坐标就复制成员对象、重建整个房间成员数组，并通过可靠 Presence 事件广播给所有连接。

客户端收到每个 Presence 包后同时调用 `setMembers` 和 Excalidraw `updateScene`。高频光标数据因此进入 React 组件树，使在线成员 UI 与整个 `TeamWhiteboardEditor` 随指针频率重复渲染；Excalidraw collaborators Map 的键还由用户 ID 和数组位置临时拼接，连接加入或离开时可能改变身份键。该链路既没有客户端发送上限，也没有服务端丢弃策略和光标专项指标，无法区分真实网络 RTT、消息排队与本地主线程开销。

### 解决方法

把低频成员名单与高频光标拆成不同事件。Presence 只在连接加入或离开时广播，并携带服务端 Socket 连接 ID 作为稳定 collaborator 键；光标事件只包含该连接的坐标、按钮、工具和单调序号。客户端实时发布器以 33 毫秒窗口保留最新坐标，普通移动使用 Socket.IO volatile 发送，使连接拥塞时直接丢弃无价值的旧位置；检测到一次真实的 `down → up` 转换时，清除仍在等待的中间坐标并可靠发送最终位置，避免远端按钮状态停留在按下。

服务端对光标单独实施每 10 秒 600 次的防御性上限，只向房间其他连接 volatile 转发一个坐标增量，不修改成员名单。接收端按连接 ID 和序号忽略旧位置，只替换内存中的 collaborators Map 并调用 Excalidraw `updateScene`；React `members` state 只处理人员生命周期变化。指标分别记录接受与丢弃的光标数量。单元与 Socket.IO 集成测试必须覆盖 33 毫秒合并、最终 `pointerup` 不被旧样本覆盖、光标增量不触发 Presence 重发以及房间成员身份键稳定；真实浏览器验收还应观察端到端光标更新频率、主线程帧耗时和受控网络抖动下是否存在可靠消息追赶。
