# 知识库维护指南

本文约束开发者和 AI 如何维护 `docs/`。目标是在“事无巨细”和“只有口号”之间保持可操作的粒度。

## 维护目标

一篇有效文档应帮助未来维护者在几分钟内回答：

1. 这个模块或决策解决什么问题？
2. 主要组件、数据和调用边界是什么？
3. 哪些规则是必须保持的不变量？
4. 为什么选择当前方案，主要代价是什么？
5. 修改时需要检查哪些代码和相邻文档？

如果文档不能改善未来决策、排错或安全性，就不应为了“覆盖率”而创建。

## 应该记录什么

满足任一条件时应记录或更新知识：

- 跨越三个或更多文件、层或运行边界的行为。
- 单看代码不容易理解的设计原因或被拒绝的替代方案。
- 权限、数据一致性、安全性或生命周期不变量。
- 会影响后续多个功能的架构决定。
- 数据库关系、迁移策略或具有风险的运维步骤。
- 已经在讨论中反复解释，未来很可能再次被问到的知识。

典型例子：

- 为什么初始项目数据在 Workspace Server Component 查询。
- 为什么所有项目 owner 都必须同时存在于 `project_members`。
- 为什么项目读取是 server-only 函数，而项目创建是 Server Action。

## 不应该记录什么

不要把知识库变成源码的逐行翻译。以下内容通常不记录：

- Tailwind 类名、颜色值、间距和一次性的 UI 微调。
- 单个显而易见的事件处理器或 props 传递过程。
- 可从一个短函数直接读出的实现细节。
- 临时调试结论、未验证猜测和本地运行状态。
- 没有进入计划或实现的远期设想。
- 经常变化的完整目录树、行号和复制的大段源码。
- 提交日志已经足够表达的机械重命名或格式化。

例外：如果一个看似局部的细节承担了安全、兼容或数据一致性约束，就应记录约束和原因，而不是记录每一行实现。

## 粒度判断

使用下面的三层尺度：

| 层级 | 处理方式 | 示例 |
| --- | --- | --- |
| 局部实现 | 依赖清晰代码、类型和必要测试 | 输入框如何更新本地 state |
| 稳定模块知识 | 写入 architecture、feature 或 database 文档 | 项目创建事务和成员查询规则 |
| 重要取舍 | 新增 ADR | 首屏数据选择 Server Component 而不是客户端 API 请求 |

一篇文档只覆盖一个稳定主题。需要同时解释多个主题时，建立索引并拆分，而不是创建超长“万能文档”。反过来，只有一两句话且没有独立生命周期的内容应合并进现有主题文档。

## AI 维护流程

AI 在修改知识库或相关代码时必须按以下顺序工作：

1. 从 [`README.md`](README.md) 找到与任务相关的文档，不批量读取所有历史资料。
2. 检查相关 Accepted ADR，将其作为设计约束和偏离检测依据，不把它当成当前实现证据。
3. 以当前工作区为唯一事实源，包括未提交代码、Schema、迁移、配置和脚本；使用 CodeGraph 和当前文件验证文档中的文件、符号、调用边界和数据模型，使用测试作为补充证据。
4. 判断变化属于局部实现、稳定模块知识还是重要架构取舍，并确认每条强不变量由数据库、应用代码、运维流程还是外部系统执行。
5. 只更新受影响的最小文档集合，并与代码放在同一次变更中；优先扩展已有稳定主题，不按目录机械生成文档。
6. 检查相对链接、状态、术语和示例是否准确，并运行与变更风险相称的类型、Lint、测试或迁移验证。
7. 在交付说明中指出更新了哪些知识、验证依据、仍未覆盖的风险，以及是否新增或替代 ADR。

AI 不得：

- 因为代码当前如此就自动改写 Accepted ADR 的理由。
- 把推测写成已经确定的事实。
- 为了显得完整而生成尚不存在的服务、接口或目录。
- 从只呈现文案或视觉状态、但不参与该能力执行的数据，以及设计参考、计划或历史记录，推断底层产品能力已经实现。
- 在不了解旧文档用途时删除历史记录。
- 复制密钥、连接字符串、用户数据或本地数据库内容到文档。

## 验证证据与冲突处理

AI 写入当前状态文档前必须能指出可复查的依据。依据优先使用稳定文件路径和符号名，不把一次命令输出、当前行号或 AI 推理过程写进长期文档。

- “当前已实现”的功能必须能在当前工作区的执行路径、数据模型或运行配置中定位；仅仅渲染某项功能的名称、说明或示意内容，不证明对应的数据和行为已经实现。
- 使用“必须”“不得”“仅允许”时，应记录执行层。若规则只由某个应用入口维持，不得暗示数据库已经强制保证。
- 安全边界既要记录受保护范围，也要记录明确排除项、公开入口和资源级授权要求。
- 测试用于证明关键路径和防止回归，但测试通过不自动证明文档中的所有业务语义。
- 证据不足时写明“未验证”或“尚未决定”，不得用最可能的推测补齐事实。

发现冲突时先区分两类问题：

1. 当前可执行状态与文档不一致：当前状态文档已经过时，应以实现为依据修正。
2. 当前代码与 Accepted ADR 不一致：代码仍代表当前实现事实，同时将其作为架构偏离报告，再决定修复代码或新增替代 ADR。

如果不能确认哪一方代表预期行为，AI 应保持冲突可见并请求决策，而不是自行选择更方便的一方。

## 更新触发规则

| 代码变化 | 文档动作 |
| --- | --- |
| 仅样式或局部重构，行为不变 | 通常不更新知识库 |
| 稳定业务流程、权限或不变量变化 | 更新对应 `features/` 文档 |
| 服务端/客户端边界或数据流变化 | 更新 `architecture/`；重大取舍新增 ADR |
| 表、关系、索引或迁移流程变化 | 更新 `database/` 和相关 feature 文档 |
| 新增外部 API、Webhook 或实时服务 | 更新 architecture、feature，必要时新增 ADR |
| 旧决策被替代 | 新增 ADR，并将旧 ADR 标记为 Superseded |
| 只修正文档错误，不改变设计 | 直接修正文档并说明依据，不新增 ADR |

## 写作要求

- 使用明确的当前时态区分“已实现”“计划中”“未决定”。
- 业务不变量使用“必须”“不得”“仅允许”等可验证语言。
- 引用稳定的仓库相对路径和符号名，不引用易漂移的行号。
- 代码片段只保留说明边界所需的最小部分。
- 每篇文档开头说明范围；结尾列出相关代码和相关决策。
- 优先使用小型流程图、表格或示例解释跨层关系，避免长篇重复叙述。
- 文件名使用小写英文和连字符；正文当前统一使用中文，代码标识保留原文。
- 图片和其他非代码素材必须由所在目录的索引说明用途、来源、授权状态和权威性；未索引素材不得作为实现依据。

## ADR 维护

- 状态只使用 `Proposed`、`Accepted`、`Superseded`、`Rejected`。
- Accepted ADR 不删除、不改写核心背景和决策。
- 决策变化时新增编号递增的 ADR，并在旧 ADR 状态中链接替代者。
- 小型实现选择不创建 ADR；只有存在真实替代方案和长期后果时才创建。

## 完成检查

维护结束前确认：

- 文档描述的是当前实现，没有把计划写成事实。
- 关键的不变量、边界和原因足够明确。
- 没有复制可从代码直接读出的琐碎细节。
- 所有链接指向存在的文件。
- 所有“必须”类规则都说明了执行层，关键路径有相称的测试或明确记录测试缺口。
- 若当前代码存在 API、Webhook 或后台任务，文档已经准确说明其身份验证、资源授权和实际路由保护范围。
- 相关 ADR 状态正确。
- 旧文档若仍保留，已清楚标记是否具有权威性。
- 设计参考和其他非代码素材已索引，且没有被误写为已实现功能。
